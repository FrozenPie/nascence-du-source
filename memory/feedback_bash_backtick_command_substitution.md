Never write a backtick-wrapped code span (markdown-style, e.g. quoting a filename or command for readability) inside a **double-quoted** bash string — in POSIX shells, backticks inside double quotes are still live command substitution, not inert text. Bash will actually execute whatever is between the backticks as a real subshell command.

**Why:** discovered for real 2026-09-04/05 in a Nascence session (F-0840). A `findings_log.py record --claim "..."` command included a markdown-style code reference like a mention of `python scripts/run_nascence.py` for readability, inside a double-quoted --claim argument. Bash parsed the backtick pair as command substitution and actually launched `scripts/run_nascence.py` as a real subprocess — which, because that script is Du's live cognition entry point, booted a **second, fully-live duplicate instance of a running production process**, concurrent with the real one, writing to the same shared state files for several minutes before it was noticed (via runaway model-loading output in a backgrounded command) and killed.

**How to apply:** when constructing any shell command (Bash tool, PowerShell, or otherwise) that embeds descriptive text mentioning a filename, command, or code snippet inside a double-quoted string, either (a) use single quotes for the outer string instead (backticks are inert inside single quotes in bash), or (b) strip backticks from the embedded text entirely and use plain wording. This applies especially to long `--claim`/`--evidence`/commit-message arguments that describe code changes — exactly the kind of text prone to habitual markdown-style backtick-quoting. Before running any command with a long embedded string, scan it for backtick characters if the outer quoting is double quotes. This is a general shell-safety lesson, not specific to this one command or project — applies to Bash tool usage in any repo.

See [[project-nascence-session-handoff-20260904-235958-dosed-coupling-habituation-decide-review-write-fence]] for the full incident (F-0840): the duplicate process was killed via stopping the background task that spawned it (a direct process-kill was blocked by the harness's own permission classifier), and post-incident checks found the live log, sqlite DB integrity, and shared JSON state files all intact — but a silent "lost update" race on a JSON state file during the ~5min overlap window was not fully ruled out (no cross-process locking on those files).

**RECURRED 2026-09-13 (J-0931/J-0934 session):** the stated mitigation ("scan for backtick characters before running") is not reliable in practice on a long, multi-paragraph `--briefing`/`--claim`/`--evidence` argument — a backtick pair mentioning `python scripts/life_smoke.py` for readability, buried in the middle of a ~10-sentence `job_queue.py spawn-job --briefing "..."` string, was missed on manual scan and bash actually re-ran that (thankfully self-isolating, non-mutating) smoke test as a real subprocess, splicing its entire stdout into the middle of the stored briefing text and corrupting it. A second backtick pair in the same string (`` `git worktree add <scratchpad>\wt_probe HEAD` ``) also fired as command substitution but happened to fail harmlessly on bash's own `<`/`>` redirection parsing of the placeholder text before `git` could run. No data damage either time (the substituted command was inert or self-isolating), but the job's own briefing was left permanently garbled with no clean way to fix it after the fact (job_queue.py has no `edit`, and hand-editing the `.jsonl` is against this project's own rules) — the mistake is not just risky, it is also hard to undo once made.

**RECURRED AGAIN 2026-09-27 (T-0065 session):** a `skill_manager.py suggest --text "..."` string containing three backticked command names (`decide.py amend ...`, `job_queue.py amend ...`, `withdraw --why`) was run inline; all three fired as command substitution ("command not found"), and the stored suggestion S-0194 was saved with blank holes where the names should be. Cleaned up by resolving S-0194 declined and re-filing as S-0195 via `--text-file`. Third occurrence; the trigger each time is a medium-length prose argument that felt too short to bother writing to a file. Rule of thumb now: any shell argument longer than one sentence goes through a file, no exceptions.

**Stronger mitigation:** do not rely on scanning long prose for backticks before running — instead, default to never using backtick-style inline-code quoting inside ANY double-quoted shell string, full stop. Use plain wording ("the script scripts/life_smoke.py") or write the long argument to a file first (`--briefing-file`/`--claim-file`/`--evidence-file`, which every one of this toolchain's own record/spawn commands already supports) and pass that file path instead of an inline string — sidesteps bash quoting entirely for anything long enough to plausibly contain a stray backtick.
