## Full descriptions (the complete 'when and why', by cluster)

### decisions

**`/decide`**  
Use to record or look up a founder ruling on a Nascence plan — 'what's Travis decided about X', 'what's waiting on a decision', 'record that we decided Y', 'is this still open', or whenever a plan's next step is a choice rather than a build. A decision ledger ported from Du's commitment ledger: a ruling is only held if it names its DEFEATER (the condition under which it gets revisited). Stops rulings made in chat from evaporating and stops 'PARKED until X' outliving X.

**`/decide-review`**  
Use when Travis wants to clear his backlog of open plan decisions in one sitting — 'what's waiting on me', 'let's go through the open decisions', 'show me what needs my call', or periodically as a batch review. Surfaces every open /decide entry as an interactive multiple-choice questionnaire (via AskUserQuestion) instead of a table he has to read and manually action, and logs each answer back into the ledger immediately. The flag that feeds this is /decide's own Open ⚖ count (already surfaced in /plan-index's Open ⚖ column) — this skill is the presentation layer on top of it, not a new store.

### misc

**`/day-timeline`**  
Use to reconstruct what happened on a given day in Nascence purely from filesystem mtimes — 'what changed today', 'what happened on 08-23', 'give me a timeline of today's work', or before trusting a narrative recap of a session that has no git history to check it against. Nascence has no git, so there is no diff to lean on; this scans real file mtimes across the whole tree for a date, classifies each touched file into a cluster by filename convention (plan slug, lab investigation, toolchain-infra file, code fix), then groups clusters into named investigations via a lookup table — same index-everything, tuple-everything discipline as memory_edges.jsonl, plan_index.md, and plan_snapshots.jsonl. An unrecognized cluster is reported under UNCLASSIFIED rather than silently dropped or guessed at.

**`/du-pulse`**  
Use to check on Du / the Nascence simulation — 'how's Du doing', 'what's happened since the last check', 'is Du still running', a Nascence health check, or any status/observation pass on the C:\\Nascence spirit. Runs a comprehensive read-only pulse (liveness, store state, the Phase-B homeostatic lock, the monoculture, world-engagement, recent inner life, what's new, flags) and interprets it with the project's verify-before-asserting discipline.

**`/findings-log`**  
Use to record an investigation finding with real evidence and an honest confidence level — 'log what we found', 'record this finding', 'we verified X', 'we think X but haven't confirmed it', or whenever an investigation surfaces something that should spawn a test/lab job rather than just live in chat. Enforces this project's own truthfulness rule (verified/inferred/guessing, CLAUDE.md's 'I know / I infer / I'm guessing') by REFUSING a 'verified' claim with no real evidence cited — the same discipline /decide applies to a ruling with no defeater. `spawn-job` turns a finding directly into a linked job-queue entry.

**`/gauge-correlate`**  
Use to find which of Nascence's HUD gauges move together — 'do any of the gauges correlate', 'find patterns across the monitors', 'what's coupled with what', 'run the gauge correlation pass' — or whenever a founder question about Nascence's ~50 operational readouts (hardware, LLM usage, affect, sleep, ignitions, per-plan monitors) is really asking 'which of these are secretly the same signal' rather than 'what is each one reading right now'. Applies UDMS's own dual-cohesion question (which files move together, from co-change evidence) to Nascence's own HUD logs instead of source code. Runs from any window/cwd — never writes to C:\\Nascence, only reads it.

**`/graphify`**  
Use for any question about a codebase, its architecture, file relationships, or project content — especially when graphify-out/ exists, where the question should be treated as a graphify query first. Turns any input (code, docs, papers, images, videos) into a persistent knowledge graph with god nodes, community detection, and query/path/explain tools.

**`/idea-log`**  
Use to capture an idea that's being talked about but isn't a plan yet — 'that's an idea, not a plan', 'log this before we lose it', 'what ideas are sitting around unpromoted', or whenever a conversation surfaces a possible direction that shouldn't just evaporate when the window closes. The pre-plan counterpart to /decide (which stops a RULING from evaporating once a question exists) — this stops the IDEA from evaporating before it's even framed as a question. `promote` links an idea to the real plan doc it became, once one gets written.

**`/job-run`**  
Use to actually WORK THROUGH job-queue's open backlog in one sitting via multiple agents — 'start a run on jobs', 'work the queue', 'clear the backlog', 'run the low-hanging jobs', 'batch through the ready jobs' — instead of `job-queue next` handing off one job at a time to a fresh window. Tiers the open+ready backlog into mechanical backfill work, small hygiene fixes, and real plan-domain analysis/build work, dispatches agents (or a Workflow) tier by tier, checks and re-kicks stale backfill jobs first, and lets the real-work tier create new jobs and edit plan docs as findings demand.

**`/memory-links`**  
Use to find what connects to something across Claude's own memory files, Nascence plans, and audit reports — 'what relates to X', 'what have we already found about this plan', 'is this session/topic connected to anything else' — instead of re-grepping many files by hand. A typed-edge store modeled directly on Nascence's own core/memory_edges.py: every link deterministically harvested with citable provenance, never guessed.

**`/nurse-rounds`**  
Use to actually WORK the mechanical, no-judgment-call slice of job-queue's backlog — 'send the nurse round', 'do the rounds', 'apply the medicine', 'clear the easy jobs', 'what can get done straight away' — as opposed to `/job-run`'s full backlog sweep or `/gauge-check`'s diagnosis pass. Dispatches a background agent or Workflow to treat every open Tier 1 (backfill) + Tier 2 (hygiene) job, refers anything that turns out to need real judgment back to the doctor/founder, and keeps a persistent round chart of what was actually treated.

**`/skill-manager`**  
Use to see what project-local skills exist under ~/.claude/skills and when/why to reach for each one — 'what skills do we have', 'which skill should I use for X', 'is there already a tool for this', 'catalog our skills', or before building a new skill (to check nothing overlapping already exists). Also catches skill directories with real code but no SKILL.md — invisible to Claude's own skill-matching, a real gap first found in `day-timeline`. Scan writes a browsable index (docs/skill_index.md) and files a `doc` job for any registration gap; never fixes a skill's content itself, only surfaces and queues the fix. Also use `suggest` to log a rough edge noticed in a skill while doing other work — 'this tool should really...', 'noting a suggestion for X' — without derailing to fix it right then.

**`/thought-log`**  
Use to capture the very first raw question, comment, or musing of a session about Du/Nascence — before it's even shaped enough to be an idea-log entry. Trigger phrases: 'I was wondering', 'what if', 'random thought', 'not sure this goes anywhere but', or any exploratory opening message that isn't already a directive to read/fix/build something specific. One rung below /idea-log: an idea is 'being talked about, not a plan yet'; a thought is 'not even framed as a question yet'. Founder wants this to fire on the FIRST message of a session by default (see global CLAUDE.md rule) — invoke it immediately, tag and link it for real, THEN continue the conversation normally.

Dry-run by default; --write folds, verbatim, append-only, after checking every cited J-/F-/D- id exists in the ledgers and that the doc has no uncommitted edits (another window may be mid-edit). Built 2026-09-27 (I-0083): world_store_write_fence.md went 459 KB / 91 sections -> 25 KB / 1 in one run, nothing lost (plan-ledger regenerates the timeline; the prose is in plan_history).

**`/plan-files-audit`**

Extracts every file a plan mentions and checks it against the real filesystem; flags empty evidence logs separately from ones with real accumulated data.

**`/plan-index`**

Read-only.
