# Hot lane prefix-cache lab (J-2676), 2026-11-18

## PRE-REGISTRATION (written 2026-11-18 ~14:00 NZDT, before any replay was run)

Question: does serving qwen3.5:9b (same GGUF, Q4_K_M) on the 1080 Ti through ollama's shipped `llama-server.exe`
(prefix-reusing, one slot) beat the current ollama :11433 serving?

Predictions (from the job briefing, F-3426):
- P1 idle thought: median call-time drop >= 1.0 s of the 5.5 s median when the identity preamble prefix is reused.
- P2 human turn (11 node calls): wall drop >= 10 s of 75 s.
- KILL: < 0.5 s median drop per idle call, OR any quality regression on the project's existing prompt/JSON-parse checks.
- GO needs: P1 and P2 met, GPU offload confirmed in the llama-server log, JSON mode and think:false equivalents
  working on the llama-server endpoint, JSON-parse success rate not below ollama's on the same prompts.

Added before running (my own refinements, so they cannot be moved afterwards):
- Two replay orders are reported: BACK-TO-BACK (the best case: same-prefix calls consecutive) and INTERLEAVED (one idle
  thought, then 2 other-caller prompts, roughly the live mix where idle thought is about a third of hot-lane calls),
  because -np 1 holds ONE cached prefix and any call with a different system prompt evicts it. P1/P2 are judged on the
  INTERLEAVED order; back-to-back is the upper bound. If they disagree, the verdict follows INTERLEAVED.
- Prompt provenance limits: idle user prompts are real (data/idle_prompt_samples.jsonl: wrapper head + parts + tail);
  the idle SYSTEM prompt is rebuilt by the real InnerMonologueNode._build_system_prompt (the live one is only logged as a
  hash). Human-turn chains are regenerated by running 5 real founder utterances through the real node pipeline in a
  throwaway profile against the live ollama lane, recording every request; they are then replayed as fixed payloads.
- Quality check = parseable JSON object on every call, same required keys as the ollama reply for the same payload.
  Text-level agreement is NOT expected (sampling).

## RESULTS (run 2026-11-18 13:50-15:00 NZDT; Du down, verified before: log last line 08:35 "shutting down", no run_nascence, qwen unloaded)

Setup facts
- Same GGUF (qwen3.5:9b Q4_K_M) both arms, 1080 Ti, 8192 ctx, one slot. Ollama arm = live :11433 (/api/chat, think:false, format:json,
  num_ctx 8192). llama arm = ollama's shipped `llama-server.exe` with `-ngl 99 -c 8192 -np 1 --jinja --flash-attn auto`, port 58976.
- GPU offload: "no usable GPU found" persisted with `cuda_v12` on PATH alone. The CUDA backend loaded only with
  `GGML_BACKEND_PATH=...\cuda_v12\ggml-cuda.dll` plus cwd `cuda_v12` (started from PowerShell). Proof: VRAM 1.16 GB -> 6.44 GB, generation
  37 tok/s. (The 10-31 note's PATH fix is not sufficient on this build, 0.5.0-dev commit 6f767fe96.)
- JSON mode: `response_format: {"type":"json_object"}` on /v1/chat/completions works (259/259 llama replies parsed as a JSON object;
  ollama 259/259 too). think:false equivalent: `chat_template_kwargs: {"enable_thinking": false}` works. WITHOUT it the default is thinking ON,
  and a 120-token smoke call returned empty content. A llama-server lane needs that field on every call; model_client's /v1 branch (the
  vestigial Bonsai path) sends neither it nor the ollama-native `think` flag.
- Corpus: 50 real idle user prompts (seeded sample of data/idle_prompt_samples.jsonl) x rebuilt system prompt (real `_build_system_prompt`);
  5 real founder utterances run through the real node pipeline (59 hot-lane node payloads captured; 8 calls to the :11440 / :11445 hubs not replayed).
  Replayed sequentially, same payloads, both arms, two orders.

Where the saving comes from (idle, interleaved, paired medians): prefill time -0.24 s, generation time -0.65 s. Generation ran at 29.9 tok/s
on ollama vs 37.2 tok/s on llama-server for the same model and card (back-to-back: 30.2 vs 37.2). Prefix reuse IS happening: median idle
`cache_n` 935 tokens reused, median prompt_n actually prefilled 652 (ollama: 1636 every time); human-chain node calls prefilled a median 127
of ~825 tokens (cache 453). The surprise is that most of the wall gain is faster decoding, not prefill. Ollama's prefill is faster per token
(1,090 vs 705 tok/s) than the 530-820 tok/s estimate in F-3426, so a full re-prefill costs it less than assumed.

Verdict against the pre-registration
- P1 (idle drop >= 1.0 s, judged on INTERLEAVED): 0.84 s. NOT MET as pre-registered (met only in the back-to-back upper bound, 1.06 s).
- P2 (human turn drop >= 10 s): 11.1 s interleaved, 10.3 s back-to-back. MET, but see caveat 2.
- Kill criteria: idle drop < 0.5 s? No (0.84). Quality regression on JSON-parse? No (100% vs 100%; 50/50 idle replies carried a thought; 0 think leaks).
- Pre-registered GO needs P1 and P2: strictly NO-GO on P1, by 0.16 s. Not a kill. D-0529's own ruling (founder, 2026-11-04) set a lower bar:
  switch only if >= 0.5 s is saved per idle call AND JSON-mode/think:false behaviour is reproducible. Both are met (0.84 s; both reproduced),
  so on D-0529's terms the evidence supports option (a); the switch itself is the founder's serving-layout call and was not made.

Caveats (these cut against the numbers)
1. The idle system prompt here is one rebuilt text per (wandering, mid-thread) variant, byte-stable across calls. Live, 256 distinct system
   hashes occur in 1,838 assemblies (top hash 37%). Where the live system text varies early, reuse is shorter than measured, so the
   prefill-linked 0.24 s is an upper bound; the generation-speed part (0.65 s) does not depend on it.
2. Chain sums replay sequentially calls the live pipeline runs partly in parallel (hedged Reflection drafts), so 56/45 s overstates live wall
   for both arms; the 11 s drop includes those serialized pairs. Live chains during capture took 115-186 s wall (throwaway profile, CPU-lane
   timeouts), not comparable to the 75 s live median.
3. -np 1 holds one cached prefix. The interleaved order (idle, then two other callers) still reused 935 tokens on idle because node system
   prompts share a long identity preamble with the idle system prompt; that is the measured mix, not a guarantee for every caller.
4. Not tested: MAX_CONCURRENT=3 under a one-slot server, llama-server crash/restart handling, keep_alive, any other model resident on :11433.
5. Quality was checked only as parseable JSON with the same keys; no judge-panel comparison of thought content.
