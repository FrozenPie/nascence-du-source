# SSD usage investigation — 2026-10-18

**Question (Travis):** what is the high SSD usage coming from, and can we spread it over both drives?
**Findings:** F-3116, F-3117, F-3118, F-3119. **Jobs:** see `job_queue.py list` for the four `finding:F-311x` entries. **Thought:** T-0098.

## Short answer

1. **The SSD is not busy.** Physical C: averaged 5% busy, 150 KB/s read, 2 MB/s write over a 60 s sample
   while Du was fully up. What *looks* like heavy disk use is Du's main python process issuing ~65 MB/s
   of `ReadFile` calls that the OS page cache answers (64 GB RAM, 43 GB free). Task Manager's per-process
   Disk column counts those, so python shows as a hog while the drive idles.
2. **The cached reads are a few uncached `json.loads` per tick** — `data/subconscious_state.json` (17.5 MB)
   is parsed by four different code paths per monologue think; `frontier.json` (5.6 MB),
   `spring_ledger_state.json` (11 MB) and `opponent_process_state.json` (8.4 MB) per co-recall;
   `transport_lines.json` every 5 s; `provisions.json` on every `stock()` call. Only `watershed.py` and
   `pursuits.py` cache theirs.
3. **The real writes (~0.6 MB/s ≈ 50 GB/day) are three whole-file state rewrites:** subconscious_state
   every ~33 s, spring_ledger + opponent_process on every co-recall. `nascence.log` is ~2 MB/day.
4. **Spreading across drives is a storage question, not an I/O one.** Both drives are the same 1 TB NVMe.
   C: has 215 GB free; D: has 60 GB free and holds only games. Of Nascence's 91 GB of data, 87 GB is cold
   archive (`_lab` 55, `backups` 19, `_trash` 9, `_snapshots` 4); the live stores are ~5 GB. Every module
   hardcodes `C:\Nascence\data`, so the live stores cannot move by config, but the cold dirs could sit
   behind an NTFS junction to D: transparently (`profile.py` checks with `relative_to`, retention moves
   with `shutil.move`). That needs D: cleared first — founder call (needs_input job).

## Method notes

- Per-process rates: `Win32_PerfRawData_PerfProc_Process` IOReadBytesPerSec/IOWriteBytesPerSec deltas
  (cumulative raw counters) — `Get-Process` has no IO fields, and `Get-Counter '\Process(*)\IO ...'`
  errors on vanishing instances.
- `py-spy` (0.4) installed to the user site for this read: `py-spy record --pid <du> --duration 30
  --rate 50 --nonblocking --format raw`, then attribute leaves to the nearest `core\`/`nodes\` frame.
- Nothing in `C:\Nascence\data` was modified; no git mutation; no process touched.
